Reviewed Rust baseline: `3a9c3c7d1cc9ee34ab801ff02ffb64114561dc16` (`devin/1793555751-stage7-mcp`). Python reference: `9a497d91a0f6e95b0949deaf8f5c431f9a4333c0` (`kv-secrets` 0.4.0).

This is a source review, not a test execution report. Descriptions below identify what the assertions exercise when executed; they do not claim that the current run passed. Paths refer to `/workspace/Kv-Rust-Mig` at the pinned Rust commit. The plan is on `origin/devin/1793529032-migration-plan:PLAN.md`, separate from the implementation branch.

## Main finding

The test suite contains substantive interoperability checks, but its current CI cannot establish that those checks executed. `.github/workflows/ci.yml:41` runs `cargo test --workspace --locked` without installing or selecting the Python reference. Tests return successfully when `KV_PY_REF` is absent, so their ordinary Rust test result is a pass rather than an explicit skip. Examples are `crates/kv-agent/tests/stage4_agent.rs:751`, `crates/kv-agent/tests/stage5_api.rs:598`, `crates/kv-mcp/tests/stage7_mcp.rs:667`, and `crates/kv-cli/tests/stage7_mcp_cli.rs:160`. Four provenance tests return without even printing a skip explanation (`crates/kv-store/tests/stage4_vault_origin.rs:100`, `:167`, `:293`, `:347`).

Passing tests also do not establish completion of the numbered migration stage. In particular, frontend parity against a shared incomplete backend can faithfully reproduce the same backend refusal.

## Assertion strengths and limits

- MCP compares complete raw stdout streams after the per-line comparison (`crates/kv-mcp/tests/stage7_mcp.rs:338`), so extra or missing response lines are caught. Its 40 generated frame seeds are deterministic test cases, not a substitute for a sustained fuzzing gate (`:712`).
- Daemon status comparison checks field sets and each retained value; only PID, session nonce and root are excluded (`crates/kv-agent/tests/stage4_agent.rs:175`).
- Owner error comparison verifies signed responses, but explicitly accepts one registration error mismatch (`stage4_agent.rs:1124`). The generated owner-request property test accepts an empty response without further assertion (`:600`), so it proves authenticity of nonempty responses, not that every malformed request receives the required response.
- The broker test asserts server request count, allowed method/path and broker-owned authorization (`crates/kv-agent/tests/stage5_api.rs:743`). This provides a useful side-effect oracle for refused requests.
- Rust-to-Python and Python-to-Rust backup restores are real cross-implementation operations, not just comparisons of Rust-produced snapshots (`crates/kv-store/tests/config_parity.rs:439`).
- Approval canonical JSON fixture iteration covers entries containing `ok`; negative entries are not all dispatched through that loop, and a separate nested-float assertion covers one negative case (`crates/kv-approvals/tests/fixtures.rs:132`). Future coverage claims should distinguish tested errors from fixture entries merely present on disk.

## Proposed revised acceptance gates

### First bounded slice: mandatory parity validation

1. Pin and attest the reference implementation before running parity: Git commit, package version, interpreter path, and actual import location. A strict mode must fail when `KV_PY_REF` is missing or unusable; optional local runs may remain optional but must not be counted as parity evidence.
2. Maintain an expected inventory of parity tests by stage and platform. Fail the gate when an expected test is absent, filtered out, unfinished or unreported. List platform exclusions explicitly. Subprocess helper entry points must not inflate substantive check counts.
3. Add Rust-written key/AEAD/TOTP verification by Python to the gate. Verify fixture provenance/inventory without regenerating tracked fixtures during baseline validation.
4. Preserve existing assertions. Record intentional scope exclusions and known divergences separately; the `owner_grant_register` error mismatch does not count as completed Stage 4 interoperability.
5. Add subprocess exit and bounded-completion assertions to MCP transcript parity. Preserve full stdout equality; unexpected stderr must be surfaced rather than discarded indiscriminately.
6. Label current shared-Rust-backend MCP tests as frontend parity. Before claiming complete backend-backed functionality, test both frontends against both backend implementations for supported operations, using independent isolated fixtures for state-changing cases.

### Subsequent implementation gates, selected after baseline results

- **Owner/grant admission:** an owner-signed, correctly bound request is admitted; malformed, forged, stale, cross-vault and cross-session requests are refused; replay, consumption and revocation effects match the reference. Remove the acknowledged registration mismatch only with the corresponding implementation and negative cases.
- **Stage 5 completion:** successful one-call permit, capability call and POST-wallet paths, plus budget exhaustion, expiry, revocation and replay cases. Refusals must be checked against an outbound-request recorder. Independently verify audit-chain correctness, not only fields with hashes omitted. Exercise the production URL-safety path with deterministic DNS/address controls.
- **Stage 6 completion:** real bubblewrap execution and its confinement/redaction/file-scan checks; no-secret, raw-secret and capability paths distinguished, and failed startup must preserve the reference's consumption semantics.
- **End-user and platform completion:** public CLI lifecycle and black-box tests against the Rust binary, hook decision corpus plus real fuzz targets, native platform gates and a release dry run. A compile-only or Unix-only pass cannot satisfy the Windows behavior gate.

These are proposed acceptance criteria, not changes to the owner's plan or evidence that the corresponding behavior already exists.

## Execution guidance for the baseline runner

- Use the pinned Rust toolchain `1.97.1` (`rust-toolchain.toml:2`) and locked dependency resolution. CI commands are fmt, clippy and workspace tests; `cargo build --release --locked` additionally exercises the release profile.
- `KV_PY_REF=/workspace/.venvs/kv-secrets/bin/python` can drive the current Rust parity tests: they invoke an interpreter with `kv` installed and do not prohibit editable installs. Its import must still be attested against the pinned Python reference.
- Use `TMPDIR=/var/tmp` for this environment. The Stage 5 `python-home` fixture still exceeded `AF_UNIX` limits under `/var/tmp/k`; `/var/tmp` fits with the five-digit PID tested. Shorten fixture basenames in the validation-gate slice so another PID digit cannot break startup. Preserve ordinary-user execution, working local sockets and the environment's process reaper. Do not remove security assertions to accommodate the execution sandbox.
- Fixture generator/checker requirements differ: `fixtures/gen/check_v040.py:44` rejects imports from the Python checkout. The fixture README prescribes a separate noneditable Python 3.10 reference installation, and the checker assumes `/var/tmp/kv-fixture-vaults/basic` (`check_v040.py:20`). Do not mistake this historical generator workspace for a prerequisite of every Rust parity test.
- No live provider credentials are needed for the existing local HTTPS integration fixture. Current execution outcomes belong in the root agent's run report, not this source-review document.
